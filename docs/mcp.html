markitdown-mcp

把 MarkItDown 包成 MCP Server：一個工具 convert_to_markdown(uri) 接上任何 MCP agent
重要：markitdown-mcp 設計給本機、受信任的 agent使用。 以 Streamable HTTP / SSE 啟動時預設只綁 localhost，不對外網曝露——請勿自行綁到其他介面， 除非你了解安全後果。

安裝與啟動

pip install markitdown-mcp

# STDIO（預設，最適合 MCP client）
markitdown-mcp

# Streamable HTTP（綁本機）
markitdown-mcp --http --host 127.0.0.1 --port 3001

單一工具：convert_to_markdown(uri)

參數 uri 可以是任何 http:、https:、file:、data: URI——與核心的 convert_uri() 一致。

Docker 啟動

docker build -t markitdown-mcp:latest .
docker run -it --rm markitdown-mcp:latest

# 存取本機檔案：掛載目錄
docker run -it --rm -v /home/user/data:/workdir markitdown-mcp:latest

接上 Claude Desktop

// claude_desktop_config.json
{
  "mcpServers": {
    "markitdown": {
      "command": "docker",
      "args": ["run", "--rm", "-i", "markitdown-mcp:latest"]
    }
  }
}

要讀本機目錄就加掛載："args": ["run", "--rm", "-i", "-v", "/home/user/data:/workdir", "markitdown-mcp:latest"]。

Debug 用 MCP Inspector

npx @modelcontextprotocol/inspector
  • STDIO：transport 選 STDIO，command 填 markitdown-mcp → Connect。
  • Streamable HTTP：URL 填 http://127.0.0.1:3001/mcp → Connect。
  • SSE：URL 填 http://127.0.0.1:3001/sse → Connect。
  • Tools 頁籤 → List Tools → 對任意有效 URI 執行 convert_to_markdown。

安全考量

  • 伺服器不支援認證，以執行者的權限運作。
  • HTTP/SSE 預設綁 localhost，但同機任何程序/使用者仍可呼叫。
  • convert_to_markdown 能讀伺服器使用者可讀的任何檔案、以及任何網路上的資料。
  • 需要更高安全時：放進 VM / 容器沙箱，限制使用者權限；絕對不要綁到非 localhost 介面。

概念解說

markitdown-mcp 把核心 MarkItDown 包裝成 MCP（Model Context Protocol）Server， 暴露單一工具 convert_to_markdown(uri)。支援三種傳輸層： STDIO（最適合 MCP client）、Streamable HTTP（REST-like）、SSE（Server-Sent Events）。

設計上只給本機、受信任的 agent 使用。伺服器無認證， 以執行者的權限運作——所以 convert_to_markdown 能讀伺服器使用者可讀的任何檔案。

實際操作 Worked Example

步驟 1：安裝與啟動 STDIO 模式

pip install markitdown-mcp

# STDIO 模式（最常用）
markitdown-mcp

步驟 2：啟動 HTTP 模式

# Streamable HTTP，綁本機
markitdown-mcp --http --host 127.0.0.1 --port 3001

# 測試：用 curl 呼叫
curl -X POST http://127.0.0.1:3001/mcp \
  -H "Content-Type: application/json" \
  -d '{"tool":"convert_to_markdown","uri":"https://example.com"}'

步驟 3：接上 Claude Desktop

// claude_desktop_config.json
{
  "mcpServers": {
    "markitdown": {
      "command": "markitdown-mcp"
    }
  }
}

常見錯誤與除錯

Connection refused: localhost:3001
確認 --host 127.0.0.1 而非 0.0.0.0。預設只綁 localhost 是安全設計。
Docker 容器內無法讀本機檔案
需要掛載目錄：-v /path/to/data:/workdir。容器內以 /workdir/ 存取。
除錯工具：
用 npx @modelcontextprotocol/inspector 可視化測試 MCP 工具呼叫。

練習與驗收

  1. 啟動 STDIO 模式，用 MCP Inspector 測試 convert_to_markdown。
  2. 啟動 HTTP 模式，用 curl 呼叫 convert_to_markdown 轉換一個 URL。
  3. 配置 Claude Desktop 連接 markitdown-mcp，實際在對話中使用。

① 進階真實情境：團隊共享的轉換服務 + Docker 掛載 + 存取控管

場景：你的團隊有 5 個 agent（Claude Desktop、自訂工具）都需要轉換文件。 你不想每台機器都裝核心，而是跑一個共享的 markitdown-mcp 服務，只對團隊內部網段開放。

# 1. 用 Docker 啟動共享服務，掛載共享資料夾
docker run -d --name md-mcp \
  -v /srv/team-data:/workdir \
  -p 127.0.0.1:3001:3001 \
  markitdown-mcp:latest \
  markitdown-mcp --http --host 0.0.0.0 --port 3001
# 2. 健康檢查：確認工具可用
curl -X POST http://127.0.0.1:3001/mcp \
  -H "Content-Type: application/json" \
  -d '{"tool":"convert_to_markdown","uri":"file:///workdir/report.pdf"}'
安全警示：上述 --host 0.0.0.0 是把服務曝露到所有介面—— 只有在你確定身處隔離的內網、且接受無認證風險時才這樣做。 官方建議是「不要綁到非 localhost 介面」；若要共享，正確做法是放在 VM/容器沙箱內、 用防火牆限制來源 IP，並讓每個 agent 透過各自的 localhost 隧道連線。

為什麼選這條路徑：MCP 的價值是單一工具 + 統一協定—— 5 個 agent 只要會 MCP 就能用，不需要各自整合 MarkItDown SDK。 掛載 /workdir 讓「本機檔案」在容器內有對應路徑，是容器化 MCP 最常踩的坑。

② 深入原理擴充：三種 transport 的差異與 URI 解析

markitdown-mcp 支援三種傳輸層，理解差異才能選對部署方式：

  • STDIO：JSON-RPC 走 stdin/stdout，最適合「MCP client 直接 spawn 子行程」的場景（Claude Desktop 就是）。
  • Streamable HTTP：POST /mcp，REST-like，適合遠端服務；預設綁 localhost。
  • SSE：Server-Sent Events，適合伺服器推送。

convert_to_markdown(uri) 內部就呼叫核心的 convert_uri()—— file: / data: / http: / https: 都能吃。

大家以為轉換沒問題但其實丟資訊
Docker 掛載路徑的錯位是 MCP 場景最典型的「假失敗」：你掛載 -v /home/user/data:/workdir， 但 agent 傳的 URI 是 file:///home/user/data/report.pdf——容器內根本沒有這個路徑， 轉換「失敗」或讀不到。不是轉換器有問題，是路徑空間不一致。解決：統一用 file:///workdir/... 作為容器內的真實路徑。

③ 診斷式疑難排解表

症狀可能原因解決方案

④ 進階挑戰題

  1. 用 MCP Inspector 分別測試 STDIO、Streamable HTTP、SSE 三種傳輸，記錄連線設定差異。
  2. 設計一個「雙層隔離」部署：markitdown-mcp 放容器內、agent 只透過 localhost 隧道連線，畫出安全邊界。
  3. 實作一個自訂 transport 包裝：攔截 convert_to_markdown 的 URI，強制把 /home 前綴改寫成 /workdir。

⑤ 專案級端到端 Worked Example：多 Agent 文件處理平台

場景：你的公司有 5 個 AI Agent（研究助理、合約審查、財務分析、會議紀錄、客服回覆）， 每個都需要轉換不同來源的文件。你要建一個共享的 markitdown-mcp 平台， 所有 Agent 透過 MCP 協定連線，統一管控——只部署一份、全部共用。

# 1. 平台架構（docker-compose.platform.yml）
version: "3.8"
services:
  markitdown-mcp:
    image: markitdown-mcp:latest
    ports:
      - "127.0.0.1:3001:3001"      # 只綁 localhost
    volumes:
      - /srv/shared-docs:/workdir:ro  # 只讀掛載
      - /var/log/md-mcp:/var/log/md:rw
    environment:
      - MAX_FILE_SIZE=52428800       # 50MB 限制
    command: markitdown-mcp --http --host 0.0.0.0 --port 3001
    read_only: true
    deploy:
      resources:
        limits:
          memory: 1G
          cpus: "1.0"
    user: "1000:1000"

# 2. 五個 Agent 的 MCP client 設定
# agent-configs/claude-desktop.json
{
  "mcpServers": {
    "markitdown": {
      "url": "http://127.0.0.1:3001/mcp"
    }
  }
}
# 其他 Agent（自訂工具）用相同 URL 連線
# 3. 健康檢查 + 監控
# 平台管理員定期執行
curl -s -X POST http://127.0.0.1:3001/mcp \
  -H "Content-Type: application/json" \
  -d '{"tool":"convert_to_markdown","uri":"file:///workdir/test.pdf"}' \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(f'chars: {len(d.get(\"markdown\",\"\"))}')"

# 預期輸出
chars: 12840   # 正常
# chars: 0     # 有問題（可能是空 PDF 或掛載錯誤）

為什麼這是「整專案規模」：第 1 輪是「Docker 掛載 + 團隊共享」； 這裡是多 Agent 統一平台、資源隔離、監控、唯讀掛載、非 root—— 不只是「能用」，而是「多人共用時不互相干擾、出問題能追溯」。 所有 Agent 只連一個端點，部署、升級、監控都只做一次。

⑥ 效能／品質／安全深度：MCP 平台的三面考量

  • 效能：MCP 的 STDIO 模式是單執行緒同步——一個 Agent 在轉換時， 其他 Agent 必須等待。Streamable HTTP 模式可並行處理多個請求，但需要 HTTP 基礎設施。 建議：STDIO 用於單 Agent 個人使用（Claude Desktop）， HTTP 用於多 Agent 共享平台。大檔（>10MB）轉換時，MCP 呼叫可能逾時—— 考慮拆檔或用非同步 transport。
  • 品質：MCP 是單一工具 convert_to_markdown(uri)—— 沒有品質閘、沒有例外分類、沒有格式特定驗證。品質控制只能在 Agent 端做 （收到 Markdown 後自己檢查字數/結構）。 建議：平台管理員在 MCP server 前加一層反向代理做統一品質驗證， 而不是信任每個 Agent 自己做。
  • 安全：MCP server 無認證——同機任何程序都能呼叫。 用 read_only 掛載 + 非 root 使用者 + 資源限制做深度防禦。 不要在 MCP URI 中暴露絕對路徑——用 /workdir/ 統一路徑空間， 避免路徑資訊洩漏到 Agent 的輸出中。
