概念解說

程式碼對照區是「文件 → 源碼」的橋樑。每個收縮塊對應一個 Python 模組或類別， 提供函式簽名、中文用途說明、以及關鍵邏輯的逐行講解。 建議搭配運作原理和架構總覽一起閱讀。

① 進階真實情境：用源碼追蹤一次真實轉換的完整呼叫鏈

場景：你在除錯「為什麼這個 CSV 轉出來格式怪怪的」。與其猜，不如沿著呼叫鏈從頭走到尾—— 把 markitdown file.csv 的每一站都標出來，找到真正負責轉換的函數。

# 追蹤路徑：CLI → MarkItDown.convert → convert_local → _convert → CsvConverter
# 1. __main__.py 解析 -x/.csv → StreamInfo
# 2. MarkItDown.convert() 收到 "file.csv"（str，非 URL）→ convert_local()
# 3. convert_local() 以副檔名建 base_guess → _get_stream_info_guesses()
# 4. magika 確認 text/csv → 與 base_guess 合併成一個 guess
# 5. _convert() 排序 converters → CsvConverter.accepts() → True
# 6. CsvConverter.convert() → csv.Sniffer 猜分隔符 → 輸出 Markdown 表格
# 實際驗證：加一行 print 觀察優先序與猜測
from markitdown import MarkItDown

md = MarkItDown()
# 複製 _convert 的行為：印出每個 converter 的接受與否
for reg in sorted(md._converters, key=lambda c: c.priority):
    print(reg.priority, reg.converter.__class__.__name__)

為什麼選這條路徑：程式碼對照頁提供了地圖，但真正要動手除錯時需要沿著邊走一遍。 把「caller → callee」的順序串起來，才能把「誰猜錯型別」「誰丟了資訊」歸因到具體函數。 這比盲目改一行測試有效得多。

② 深入原理擴充：讀源碼時的三個「認知陷阱」

程式碼對照的目的不是背函數名，而是建立正確的因果模型。三個常見誤區：

  • 「簽名會騙人」：convert(source) 看起來是「一個參數」，其實內部依型別分派到四個不同路徑—— 讀源碼不能只看簽名，要看 isinstance / 前綴判斷的分支。
  • 「順序假設」：register_converter 用 insert(0, ...) + 穩定排序， 所以「後註冊者優先」。不看呼叫順序，會誤判誰先被嘗試。
  • 「單檔誤導」：_markdownify.py 不只服務 HtmlConverter—— 它是 DocxConverter、EpubConverter 的共同父類邏輯。改它的行為，會同時影響多個格式。
大家以為轉換沒問題但其實丟資訊
「異常處理 ≠ 轉換失敗」的誤判：_convert() 的 except Exception 會把 converter 的失敗 記成 FailedConversionAttempt 後繼續試下一個。當你看到 FileConversionException 時， 裡面的 attempts 可能是「多個 converter 都失敗」的疊加——但最後成功的可能是最後一個嘗試。 如果你只讀第一個 attempt 就下結論，就會把「其實轉成功了」誤判成「失敗」。 正確做法：先看有沒有人成功，再看失敗紀錄找原因。

③ 診斷式疑難排解表

症狀可能原因解決方案
找不到某個函數的定義版本不一致（本站對齊 fd239d5/v0.1.7）確認本地版本；函數名可能在新舊版本間改名
改 _markdownify 影響了非 HTML 格式Docx/Epub 繼承自 HtmlConverter先畫繼承圖，確認誰共用此行為，再決定改哪裡
誤以為某 converter 會先被嘗試忽略 priority 與註冊順序印出 sorted(md._converters, key=lambda c: c.priority)
錯誤訊息指向多個 converter容錯鏈疊加多個 attempt先確認有無成功轉換；再看 attempt 找根因
函數行為與文件描述不符讀的是簽名不是分支邏輯看 isinstance/前綴判斷分支；用測試或 print 驗證
