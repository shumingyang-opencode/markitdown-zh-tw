概念解說

實作案例頁的目的是「用真實工具產出，不是示意圖」。 本站用 markitdown 0.1.7 在本機 uv venv 實跑 11 種格式，提供原始輸入和轉換結果的前後對照。 這是理解 MarkItDown 實際行為的最佳方式——比讀文件更直觀。

五類案例涵蓋：Office 文件、PDF/網頁、媒體/封裝、dogfood（轉自己）、 以及用 graphify 掃描 MarkItDown 源碼的知識圖譜。

常見錯誤與除錯

輸出與案例頁不同
版本差異是主因。本站釘選 v0.1.7（上游 fd239d5），你本地的版本可能不同。執行 markitdown -v 確認。
案例頁的 worked/ 目錄
所有原始輸入檔和轉換輸出都放在 worked/conversions/ 和 worked/dogfood/，可直接下載對照。

練習與驗收

  1. 下載 worked/conversions/ 中的一個 DOCX，本地轉換後比較輸出差異。
  2. 找一份自己的 PDF，用 markitdown 轉換並觀察表格處理效果。
  3. 閱讀 dogfood 案例，理解「用工具轉自己」的 meta 示範。

① 進階真實情境：把案例重現自動化——從手動轉換到回歸測試

場景：案例頁的 11 種格式是你「真實輸出」的承諾。但手動重跑很容易漏——某天換了版本， 某個輸出悄悄變了。你要把這些案例變成自動化回歸測試，每次改動都驗證。

# tests/test_conversions.py（節錄）
import subprocess, pathlib, sys

CASES = [
    ("office/sample-report.docx", "##", "#"),   # DOCX：標題結構
    ("pdf/report.pdf",           "|",  "---"),  # PDF：表格分隔列
    ("archive/archive.zip",      "Content from", None),
]

def test_real_conversions():
    for rel, must_contain, must_not in CASES:
        out = subprocess.run(
            [sys.executable, "-m", "markitdown", f"worked/conversions/{rel}"],
            capture_output=True, text=True,
        ).stdout
        assert must_contain in out, f"{rel}: missing {must_contain!r}"
        if must_not:
            assert must_not not in out, f"{rel}: unexpected {must_not!r}"

為什麼選這條路徑：把「真實輸出」變成可斷言的契約，版本升級時立即暴露行為變化—— 這正是案例頁存在的意義。用 assert 檢查「該有的結構在、不該有的結構不在」， 比肉眼比對可靠得多；搭配 markitdown -v 釘版本，回歸測試就是你的「行為快照」。

② 深入原理擴充：案例輸出背後的 converter 行為細節

案例頁的每個輸出都對應一條真實的 code path：

  • PDF：pdfminer 抽文字、pdfplumber 抽表格，兩者疊加再跑 _merge_partial_numbering_lines—— 這就是為什麼 report.pdf 的表格是「逐格換行」而不是 Markdown 表格（pdfplumber 抽不到結構化格子）。
  • 音訊：tone.wav 有轉錄依賴時拋 UnknownValueError、無依賴時優雅降級只輸出 metadata—— 同一個檔案「成敗取決於依賴安裝與否」。
  • ZIP：解壓到暫存、逐檔遞迴轉換、保留結構、結束清理——輸出以「Content from the zip file」分節。
大家以為轉換沒問題但其實丟資訊
XLSX 的合併列與 NaN：案例的 sales-data.xlsx 輸出中，Total 列是「合併儲存格」。 pandas 讀進來後合併格被展開、其餘儲存格變 NaN——表格「成功」轉出來了， 但「這是一列橫跨的總計」的語意消失了。輸出看起來正常，少了的是結構資訊。 這是最難發現的資訊遺失：它不報錯，只靠讀者對照原始檔案才看得出。

③ 診斷式疑難排解表

症狀可能原因解決方案
本地輸出與案例頁不同版本差異對齊 v0.1.7（上游 fd239d5）；markitdown -v 確認
音訊檔案有時成功有時拋例外有無安裝 [audio-transcription]統一環境；無轉錄需求就別裝該 extras
XLSX 出現 NaN 行合併儲存格展開後處理過濾 NaN；或接受為「誠實輸出」
圖片無 EXIF 段缺 exiftool 或 EXIFTOOL_PATH 未設定安裝 exiftool；案例用環境變數指定
ZIP 內的子檔沒被轉換副檔名無法被辨識確認子檔格式有對應 converter；ZipConverter 逐檔遞迴

④ 進階挑戰題

  1. 把案例擴充成「golden file」測試：把目前的輸出存成基準檔，之後每次跑都 diff，寫出測試腳本。
  2. 重現 tone.wav 的兩種行為（有/無轉錄依賴），比較 stdout 與例外，寫成對照測試。
  3. 用 markitdown 轉 MarkItDown 自己的 README.md，觀察「Markdown 轉 Markdown」會發生什麼（是否原樣保留），並解釋原因。

⑤ 專案級端到端 Worked Example：案例回歸管線 + 版本釘選 + CI 守門

場景：案例頁的 11 種格式真實輸出是你的「行為承諾」。但手動重跑容易漏——某天換了版本， 某個輸出悄悄變了。你要建一條自動化回歸管線： 每次改動都重跑所有案例、與 golden 基準 diff、差異超過門檻就讓 CI 失敗。
