四個套件 + 一條調度鏈

套件組成

repo 用 monorepo 結構，packages/ 下有四組獨立套件（都可各自 pip 安裝）：

套件PyPI 名稱職責
packages/markitdown/markitdown核心：MarkItDown 類別 + 22 個內建轉換器 + CLI
packages/markitdown-mcp/markitdown-mcpMCP Server：把核心包成 convert_to_markdown(uri) 工具
packages/markitdown-ocr/markitdown-ocrOCR 外掛：LLM Vision 抽取 PDF/DOCX/PPTX/XLSX 內嵌圖片文字
packages/markitdown-sample-plugin/markitdown-sample-plugin外掛開發範本：RtfConverter 完整範例

設計要點

  • 策略模式：converter 是可插拔策略，內建/外掛都走同一協定。
  • 依賴延後：每個格式的第三方函式庫放在 extras，沒裝只是「該格式不支援」，不影響其他格式。
  • 寬進嚴出：型別猜測給多個線索依序嘗試，converter 失敗容錯，最後才統一報錯。

概念解說

MarkItDown 的架構核心是策略模式：每個格式由一個獨立的 DocumentConverter 子類處理， 由 MarkItDown 類別統一調度。四個套件各司其職——核心包提供 22 個內建轉換器， MCP 包把核心包裝成 HTTP/STDIO 服務，OCR 包用 LLM Vision 增強圖片文字抽取， sample-plugin 則是外掛開發的起點。

關鍵設計原則：依賴延後（沒裝的格式只是不支援，不影響其他格式）、 後註冊者優先（外掛可以覆蓋內建 converter）、 容錯鏈（單一 converter 失敗不阻斷整個流程）。

常見錯誤與除錯

ModuleNotFoundError: No module named 'mammoth'
原因是沒安裝對應 extras。執行 pip install 'markitdown[all]' 安裝全部依賴， 或只裝需要的：pip install 'markitdown[docx]'。
UnsupportedFormatException
表示所有 converter 的 accepts() 都回傳 False。檢查副檔名是否正確、 是否忘了 -x 旗標提示副檔名（stdin 場景）。

① 進階真實情境：自建轉換微服務 + 外掛優先權設計 + CI 驗證

場景：你的團隊要建一個「文件轉換 API」，把 DOCX/PDF/掃描件都轉成 Markdown。 架構設計的關鍵決策：內建 converter 當底層、外掛處理特殊格式、並用 priority 控制覆寫順序。

# 1. 定義服務骨架：核心 + 外掛 + 驗證
from markitdown import MarkItDown
from markitdown._base_converter import DocumentConverter, DocumentConverterResult
import io

class PdfQualityGateConverter(DocumentConverter):
    """priority=-1.0 搶在內建之前：掃描 PDF 先檢查文字層，太薄就丟給 OCR 外掛。"""
    priority_hint = -1.0
    def accepts(self, file_stream, stream_info, **kwargs):
        return stream_info.extension in (".pdf",) or stream_info.mimetype == "application/pdf"
    def convert(self, file_stream, stream_info, **kwargs):
        # 示意：回傳「需要 OCR」的標記，讓管線決定路由
        return DocumentConverterResult(markdown="\u3010needs-ocr\u3011")

md = MarkItDown(enable_plugins=True)
md.register_converter(PdfQualityGateConverter(), priority=-1.0)

# 2. 驗證優先權生效：內建 PDF(0.0) 被 -1.0 壓在後面
print([c.converter.__class__.__name__ for c in md._converters])
# 3. 整合進 CI：每次改架構都跑一回歸測試
# pytest test_architecture.py
def test_priority_order():
    md = MarkItDown()
    names = [c.converter.__class__.__name__ for c in md._converters]
    assert "PdfQualityGateConverter" in names
    assert names.index("PdfQualityGateConverter") < names.index("PdfConverter")

為什麼選這條路徑：架構頁的核心是「可插拔策略 + priority 排序」。 用外掛搶先內建來做品質閘，能不改動核心套件就介入調度；用 CI 回歸測試把「後註冊者優先」的規則變成可自動驗證的契約。

② 深入原理擴充：調度鏈的「隱藏契約」

架構上最容易被忽略的兩條隱藏契約：

  • 後註冊者優先：register_converter() 用 insert(0, ...) 插到清單頂端。 加上穩定排序（同 priority 保持註冊順序），同為 0.0 時最後註冊的最先試—— 這就是外掛能覆蓋內建 converter 的根本機制。
  • 依賴延後：每個 converter 的第三方函式庫各自在 extras。沒裝 mammoth 只是「DOCX 不支援」， 其他 21 個 converter 照常運作——架構讓「部分失敗」成為可接受的狀態。
大家以為轉換沒問題但其實丟資訊
架構層級的「假成功」：enable_builtins() 重複呼叫只會 warn() 不報錯； 外掛載入失敗（entry_point.load() 拋例外）也只 warn() 並跳過。 你可能以為外掛在優先序最前面，其實它從沒被載入——整批轉換都走了內建， 輸出「正常」但品質遠低於預期。除錯時務必檢查 markitdown --list-plugins。

④ 進階挑戰題

  1. 在 MarkItDown.__init__() 之後手動呼叫 enable_builtins() 兩次，觀察 warn 訊息與 converter 數量變化。
  2. 寫兩個同為 priority=0.0 的外掛，反序註冊，驗證穩定排序下誰先被嘗試，並解釋原理。
  3. 設計一個「回歸測試矩陣」：對每個內建 converter，驗證「裝了 extras」與「沒裝 extras」兩種環境下 accepts() 的行為是否如預期。

⑤ 專案級端到端 Worked Example：四套件組合成「單一轉換平台」

場景：把架構頁的四個套件（核心 / MCP / OCR 外掛 / sample-plugin）真正組合成一個 「單一轉換平台」（md-platform），供本機批次、服務端 agent、雲端三種消費方式共用—— 端到端整合 Python API、MCP、雲端與外掛。

# 1. 共用核心服務層（核心套件，被三種介面重複使用）
# service.py —— 唯一的轉換實作，三種入口都呼叫它
from markitdown import MarkItDown
from markitdown.converters import ContentUnderstandingFileType

class DocService:
    def __init__(self, cu_endpoint=None):
        self.md = MarkItDown(enable_plugins=False)
        self.cu = MarkItDown(cu_endpoint=cu_endpoint,
                             cu_file_types=[ContentUnderstandingFileType.PDF]) if cu_endpoint else None
    def convert(self, local_path):      # 本機批次
        return self.md.convert_local(local_path).markdown
    def convert_cu(self, local_path):   # 雲端升級
        return self.cu.convert_local(local_path).markdown
# 2. 三種消費介面
#   a) CLI（markitdown 套件）    → 內部其實就是 DocService.convert()
#   b) MCP（markitdown-mcp）     → convert_to_markdown(uri) 轉呼叫 DocService
#   c) OCR 外掛（markitdown-ocr）→ 以 priority -1.0 攔截內建，讓 DocService 自動受惠
# 3. 預期輸出：同一份 scanned.pdf 三介面一致升級
python batch.py scans/            # 走 service.convert → OCR 外掛攔截 → 內建
curl -X POST localhost:3001/mcp -d '{"tool":"convert_to_markdown","uri":"file:///workdir/scans/1.pdf"}'
# 三條路都輸出含 *[Image OCR]...* 區塊，行為完全一致

為什麼這是「整專案規模」：第 1 輪聚焦「priority 排序」單一機制； 這裡證明架構的價值在於重複利用——把核心邏輯放在一個 DocService， CLI / MCP / 外掛三種介面都只是薄殼，改一個地方、三處同步生效。 這正是 monorepo 四套件的分工意義。

⑥ 效能／品質／安全深度：架構層的三面決策

  • 效能：pip install 'markitdown[all]' 讓所有格式就緒，但犧牲啟動與記憶體； 依賴延後 讓「只裝需要的 extras」更輕量。容器化（Docker）可同時取得「全功能」與「乾淨隔離」。
  • 品質：容錯鏈是架構的品質保證——單一 converter 失敗不拖垮整個流程， 且 FileConversionException.attempts 保留所有失敗原因。但「後註冊者優先」若沒被理解， 可能讓外掛默默覆蓋內建行為而不自知。
  • 安全：架構決定攻擊面——外掛套件以你的權限執行程式碼；MCP 無認證； convert_uri() 可觸發本機+網路雙重 I/O。架構設計時就要畫出信任邊界，詳見安全模型。
