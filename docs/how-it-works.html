運作原理

MarkItDown 的 convert() 是「把檔案交給『對的』converter」的調度器

MarkItDown 的核心不是「讀懂檔案」，而是「猜測檔案是哪種格式，然後交給對應的 converter」。 所有格式都遵循同一個 DocumentConverter 協定（accepts() + convert()）， 由 MarkItDown._convert() 依優先序逐一嘗試，直到有人成功。

調度管線五步驟

1. 建立 StreamInfo 猜測清單（線索卡）

StreamInfo 是描述「這個檔案看起來是什麼」的資料結構，欄位含 mimetype / extension / charset / filename / local_path / url。 來源可以是副檔名、Content-Type header、Content-Disposition 的 filename、或 URL 的副檔名。

StreamInfo(
    mimetype="application/pdf",
    extension=".pdf",
    filename="report.pdf",
    local_path="report.pdf",
)

2. magika 讀位元組補強猜測

_get_stream_info_guesses() 會再呼叫 magika（Google 的內容型別偵測模型， 純本機、零網路）直接讀檔案位元組猜型別，並用 charset-normalizer 猜文字編碼。 如果 magika 的猜測與線索衝突（例如副檔名說 .txt 但內容是 HTML）， 就會產生多個 guess，依序嘗試。

3. 依 priority 排序 converters

每個 converter 註冊時帶一個 priority：越小越先試。 內建 converter 大多為 0.0（特定格式）；PlainTextConverter / HtmlConverter / ZipConverter 是 10.0（通用兜底，放最後）。排序是穩定排序，同優先級保持註冊順序、後註冊者在前。

4. 依序問 accepts()，接受就 convert()

對每個 guess × 每個 converter，先問 converter.accepts(file_stream, stream_info) （通常用 mimetype / extension 判斷），接受後呼叫 converter.convert(...) 得到 Markdown。 任一 converter 拋例外時不會立刻失敗——被記錄為 FailedConversionAttempt，繼續試下一個。

5. 輸出標準化 + 錯誤聚合

成功後會把輸出做標準化：去掉每行行尾空白、把連續 3+ 個換行壓成 2 個。 全部 converter 都失敗時，若有失敗紀錄 → 拋 FileConversionException（內含所有嘗試）； 完全沒人接受 → 拋 UnsupportedFormatException。

圖解： 
convert("report.pdf")
  └─ 線索：副檔名 .pdf + magika 內容偵測
  └─ guesses = [StreamInfo(.pdf), StreamInfo(magika 猜測)]
  └─ 依 priority 排序 converters：[PDF, DOCX, XLSX, ..., PlainText(10), Html(10), Zip(10)]
  └─ PDF.accepts() → True → PDF.convert() → Markdown 字串
  └─ 標準化輸出 → DocumentConverterResult(markdown=..., title=...)

容錯鏈：converter 失敗不代表整個轉換失敗

這是 MarkItDown 最體貼的設計：某個 converter 在 convert() 中途拋例外時， 該例外被 except Exception 接住、包成 FailedConversionAttempt 存進清單， file_stream 會 seek 回原位置，繼續試下一個 converter。 最後若全軍覆沒才統一拋 FileConversionException(attempts=...)，方便你一次看到所有失敗原因。

English original — the fail-safe loop 
for stream_info in stream_info_guesses + [StreamInfo()]:
    for converter_registration in sorted_registrations:
        converter = converter_registration.converter
        if converter.accepts(file_stream, stream_info, **_kwargs):
            try:
                res = converter.convert(file_stream, stream_info, **_kwargs)
            except Exception:
                failed_attempts.append(FailedConversionAttempt(
                    converter=converter, exc_info=sys.exc_info()))
            finally:
                file_stream.seek(cur_pos)
        if res is not None:
            res.text_content = normalize(res.text_content)
            return res
if failed_attempts:
    raise FileConversionException(attempts=failed_attempts)
raise UnsupportedFormatException(...)

依賴式輸出：圖片與音訊

圖片與音訊的輸出「依賴本機工具或 LLM」：

  • 圖片：EXIF 中繼資料需要 exiftool；描述需要 llm_client + llm_model（multimodal LLM）。兩者都缺 → 輸出為空。
  • 音訊：EXIF 需要 exiftool；轉錄需要 SpeechRecognition（預設 Google Web API）。轉錄失敗的例外不一定被吞掉（見媒體案例）。

為什麼選 Markdown？

Markdown 非常接近純文字、token 效率高，同時又能表達標題、清單、表格、連結等結構； 主流 LLM（如 GPT-4o）原生「會講」Markdown。這是它存在的根本理由。

概念解說

MarkItDown 的 convert() 不是「直接讀檔案」，而是「猜測格式 → 依序嘗試 → 容錯」的管線。 五個步驟：(1) 建立 StreamInfo 線索卡、(2) magika 讀位元組補強猜測、(3) 依 priority 排序 converters、 (4) 逐一問 accepts()，接受就 convert()、(5) 輸出標準化 + 錯誤聚合。

這個設計的關鍵價值是容錯鏈：某個 converter 在 convert() 中途失敗時， 例外被接住、file_stream seek 回原位，繼續試下一個。最後才統一拋出包含所有嘗試的例外。

# → FailedConversionAttempt 被記錄

步驟 3：手動觸發 UnsupportedFormatException

import io
stream = io.BytesIO(b"\x00\x00\x00\x00")
from markitdown import StreamInfo
try:
    md.convert_stream(stream, stream_info=StreamInfo(extension=".fake"))
except Exception as e:

常見錯誤與除錯

FileConversionException vs UnsupportedFormatException
UnsupportedFormatException：沒有任何 converter 的 accepts() 回傳 True（格式完全不認識）。
FileConversionException：有 converter 接受了但 convert() 失敗（通常是缺少依賴或檔案損毀）。
除錯技巧：
FileConversionException.attempts 包含所有失敗的 converter 和例外資訊，是定位問題的最佳起點。

① 進階真實情境：批次 PDF 轉換 + 品質驗證 + CI 管線

場景：公司每天新增 2000 份報價單 PDF，要轉成 Markdown 餵給 RAG 檢索。 「轉換完就信任」是最大的坑——掃描版 PDF 會「成功」回傳空字串，必須先驗證品質再進檢索索引。

from pathlib import Path
from markitdown import MarkItDown
from markitdown._exceptions import FileConversionException, UnsupportedFormatException

md = MarkItDown()
ok, empty, failed = [], [], []

for pdf in Path("invoices/").glob("*.pdf"):
    try:
        text = md.convert_local(str(pdf)).markdown      # 最窄 API，安全守則
        (ok if len(text.strip()) >= 50 else empty).append(pdf.name)  # 字數閘
    except (FileConversionException, UnsupportedFormatException) as e:
        failed.append((pdf.name, type(e).__name__))

print(f"OK {len(ok)} / empty {len(empty)} / failed {len(failed)}")
# empty 清單幾乎都是掃描版 PDF——轉換「成功」但內容是空的

批次中把例外分類收集而不直接中斷，才能一次跑完 2000 份再統一處理。 品質閘（字數門檻）之所以必要，是因為 _convert() 的容錯鏈設計—— converter 失敗會被接住並繼續試下一個，失敗不一定會拋到你面前。

# 整合進 CI：回歸守門員
# scripts/convert_invoices.py 跑完後輸出品質統計
# 若 OK 比例低於門檻 → 讓 CI 失敗，阻止壞資料進索引
def quality_gate(ok_count, total, threshold=0.95):
    if ok_count / total < threshold:
        raise SystemExit("品質回歸！轉換成功率低於門檻")

為什麼選這條路徑：convert_local() 是最窄、可重現的入口（符合安全守則）； 用字數閘捕捉「假成功」；用例外分類讓 2000 份的批次可除錯；最後用 CI 門檻把品質變成可量測的守門員。

② 深入原理擴充：HTML→Markdown 引擎與「假成功」

所有「HTML 家族」converter（HtmlConverter 及其繼承者 DocxConverter、EpubConverter） 都共用同一套 _markdownify.py 的 _CustomMarkdownify 引擎。它覆寫了 markdownify 的四個行為：

  • convert_hn — 標題保留為 #（含 lang 屬性）。
  • convert_a — 保留連結、移除 javascript: 連結、轉義 URI。
  • convert_img — 圖片輸出 ![alt](src)，處理 data URI（可截斷）。
  • convert_input — checkbox 轉成 [x]/[ ]。
大家以為轉換沒問題但其實丟資訊
最典型的「假成功」是掃描版 PDF：pdfminer 抽不到文字層、pdfplumber 抽不到表格， PdfConverter.convert() 仍會正常回傳——只是內容幾乎是空的。沒有例外、沒有警告。 要發現它只能靠頁數比對（pdfplumber 知道頁數、輸出卻沒內容）或字數驗證。 這是「轉換成功 ≠ 內容完整」的最佳教材。

⑤ 專案級端到端 Worked Example：智慧路由文件服務

場景：把「調度管線」知識放大成一個整專案——「文件智慧路由服務」（doc-router）。 它不只轉檔，還依據 StreamInfo 猜測與品質閘自動決定走哪條路： 本機內建 → OCR 外掛 → Azure 雲端，三級路由，端到端整合 轉換器、 Python API、雲端與安全。

# 1. 管線骨架：同一份文件走三級路由
def route_convert(md, path):
    text = md.convert_local(path).markdown          # 第一級：本機內建
    if quality_ok(path, text):                       # 品質閘過 → 完成
        return text, "local"
    text = md.convert_local(path, enable_plugins=True)  # 第二級：OCR 外掛
    if quality_ok(path, text):
        return text, "ocr"
    return md.convert_local(path, use_content_understanding=True).markdown, "cu"  # 第三級：雲端

# 2. 品質閘：結合「頁數 vs 字數」與結構檢查
def quality_ok(path, text):
    import pdfplumber
    with pdfplumber.open(path) as pdf:
        pages = len(pdf.pages)
    words = len(text.split())
    return words >= 30 and words >= pages * 40        # 每頁至少 40 字
# 3. 預期輸出（對 3 種文件各跑一次）
報告: electronic.pdf   → local (12 頁, 3840 字)   OK
報告: scanned.pdf      → local 品質不足 → ocr → cu (11 頁, 2105 字)  UPGRADED
圖片: layout.png       → local (EXIF+LLM 描述)                        OK

為什麼這是「整專案規模」：第 1 輪是「在批次裡偵測空字串」； 這裡把偵測→升級→路由決策串成一條可營運的服務——品質閘同時是路由開關， 三級路徑各自對應一篇 docs（內建/外掛/雲端），最後只剩真正需要付費的文件才上雲。

⑥ 效能／品質／安全深度：調度層的三面檢視

  • 效能：每次 convert() 的成本 = guesses × converters 的嘗試次數。 guess 越多、兜底 converter 越多，失敗成本越高；先給對的 StreamInfo（-x / stream_info） 可讓第一個 guess 就命中，省掉整串嘗試。大檔批次時考慮併發，但注意 _convert 內有 seek， 非執行緒安全，併發要用 process pool 而非 thread pool。
  • 品質：normalize() 只做「行尾空白 + 連續換行」的輕量標準化，不保證語意完整。 品質必須自己加閘（字數、結構、頁數比對）——這是本站反覆強調的「假成功」對策。
  • 安全：accepts() 也是外部程式碼（外掛時）；magika 是純本機模型不發網路。 但 convert_uri() 的 http/https 猜測會真的抓取——伺服器場景務必先消毒輸入。
