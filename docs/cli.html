CLI 指令參考

markitdown 是 argparse 寫的命令列工具，讀 stdin 或檔案、輸出 stdout 或 -o 檔

基本語法

SYNTAX:
    markitdown <OPTIONAL: FILENAME>
    若不給 FILENAME，從 stdin 讀取。

EXAMPLE:
    markitdown example.pdf
    cat example.pdf | markitdown
    markitdown < example.pdf
    markitdown example.pdf -o example.md
    markitdown example.pdf > example.md

旗標一覽

旗標用途
-v, --version顯示版本號並離開
-o, --output FILE輸出到檔案（UTF-8）；否則寫 stdout
-x, --extension EXT提示副檔名（stdin 讀取時很有用），自動補上 .
-m, --mime-type TYPE提示 MIME type（格式必須含 /）
-c, --charset CS提示編碼（如 UTF-8），用 codecs 正規化
-d, --use-docintel改用 Azure Document Intelligence（需 -e 端點）
-e, --endpoint URLDocument Intelligence Endpoint（-d 必填）
--use-cu, --use-content-understanding改用 Azure Content Understanding（需 --cu-endpoint）
--cu-endpoint URLContent Understanding Endpoint（--use-cu 必填）
--cu-analyzer ID指定 CU analyzer ID；預設依檔案類型自動選
--cu-file-types TYPES只讓這些格式走 CU（逗號分隔，如 pdf,jpeg,mp4）
-p, --use-plugins啟用第三方外掛（預設關閉）
--list-plugins列出已安裝外掛後離開
--keep-data-uris保留 base64 data URI（預設截斷）
注意：-d 與 --use-cu 是互斥群組，不能同時用。

常用範例

# 基本轉換
markitdown report.pdf -o report.md

# 從 stdin 讀取並提示副檔名
cat data.bin | markitdown -x .csv

# 轉換網址（CLI 直接吃 http/https/file/data URI）
markitdown https://github.com/microsoft/markitdown -o page.md

# 開外掛
markitdown --use-plugins document.pdf

# 用 Azure Document Intelligence
markitdown file.pdf -o out.md -d -e "https://<resource>.cognitiveservices.azure.com/"

# 用 Azure Content Understanding（指定 analyzer）
markitdown invoice.pdf --use-cu --cu-endpoint "<endpoint>" --cu-analyzer "my-invoice-analyzer"

概念解說

MarkItDown CLI 是一個 argparse 寫的命令列工具，核心邏輯很簡單： 解析參數 → 建 MarkItDown 實例 → 呼叫 convert → 輸出到 stdout 或檔案。 支援 stdin 管道、本機檔案、URL，以及 Azure 雲端服務。

關鍵旗標：-x（提示副檔名，stdin 時必備）、-o（輸出到檔案）、 -p（啟用外掛）、-d/--use-cu（Azure 雲端路徑）。

實際操作 Worked Example

步驟 1：基本轉換

# 轉換本機 PDF
markitdown report.pdf -o report.md

# 轉換網址
markitdown https://github.com/microsoft/markitdown -o github.md

步驟 2：stdin 管道（關鍵：-x 提示副檔名）

# 從 stdin 讀取，提示是 CSV
cat data.bin | markitdown -x .csv -o data.md

# 從 stdin 讀取，提示 MIME type
cat file.bin | markitdown -m "application/pdf" -o out.md

步驟 3：外掛模式

# 先列出已安裝外掛
markitdown --list-plugins

# 使用外掛轉換
markitdown document.pdf --use-plugins -o out.md

常見錯誤與除錯

stdin 讀取時格式偵測失敗
沒有副檔名線索時 magika 可能猜錯。務必加 -x .ext 或 -m "type/subtype" 提示。
-d 與 --use-cu 不能同時用
兩者是互斥的雲端路徑。Document Intelligence（-d）和 Content Understanding（--use-cu）只能擇一。
輸出亂碼？
加 -c UTF-8 強制指定編碼。CLI 預設用 UTF-8 輸出，但輸入編碼偵測可能不準。

練習與驗收

  1. 用 markitdown -v 確認版本，再用 markitdown --help 瀏覽所有旗標。
  2. 找一個 CSV 檔案，分別用 -x .csv 和不加 -x 轉換，比較結果。
  3. 用管道 echo "hello" | markitdown 測試 stdin 模式。

① 進階真實情境：批次轉換工作流 + 品質門檻 + CI 整合

場景：你要把一整個目錄（含子目錄）的 PDF 與 Office 檔批次轉成 Markdown， 並在 CI 裡檢查「每個檔案都轉出非空結果」，失敗就讓建置失敗——避免壞轉換靜默進資料庫。

# 1. 批次轉換 + 品質門檻
#!/usr/bin/env bash
set -euo pipefail
FAILED=0
find docs/ \( -name "*.pdf" -o -name "*.docx" -o -name "*.xlsx" \) -print0 |
while IFS= read -r -d '' f; do
  out="${f%.*}.md"
  markitdown "$f" -o "$out" || { echo "FAIL convert: $f"; FAILED=1; continue; }
  # 品質門檻：空輸出視為失敗（掃描 PDF 常見）
  if [ ! -s "$out" ]; then echo "FAIL empty: $out"; FAILED=1; fi
done
exit $FAILED
# 2. 整合進 CI（GitHub Actions 節錄）
- name: Convert docs to Markdown
  run: bash scripts/batch-convert.sh
- name: Fail on empty conversions
  run: |
    if grep -rl "FAIL empty" logs/; then exit 1; fi

為什麼選這條路徑：CLI 比 Python API 更適合 CI——無狀態、可被 shell 工具鏈組合、 退出碼可直接驅動建置結果。用 -o 指定輸出避免 stdout 混入日誌； 用 -x 只在需要提示副檔名的 stdin 場景使用。

② 深入原理擴充：CLI 如何把旗標變成 StreamInfo 線索卡

CLI 不是把檔案丟給 API 那麼簡單——它負責把命令列旗標翻譯成 StreamInfo 線索，餵給 _convert()：

  • -x：自動補上 . 前綴後寫進 extension 欄位。
  • -m：寫進 mimetype（會驗證格式必須含 /）。
  • -c：用 codecs 正規化成 canonical 編碼名（避免 utf-8 vs UTF8 的比對陷阱）。
  • stdin 讀取時先灌進 BytesIO，確保 magika 可以重複讀位元組做內容偵測。
大家以為轉換沒問題但其實丟資訊
stdin + 猜錯類型是最隱蔽的資訊遺失：cat file.bin | markitdown 沒給 -x， magika 只能靠位元組猜。若猜成 text/plain，檔案會被 PlainTextConverter 當純文字「成功」轉出—— 不會報錯，但二進位內容變成亂碼文字，結構資訊全沒了。永遠記住：stdin 場景 + 非純文字檔 = 必加 -x。

③ 診斷式疑難排解表

症狀可能原因解決方案
stdin 轉出亂碼或空白magika 猜錯類型，走了 PlainText加 -x .pdf / -m "application/pdf" 提示
-d 與 --use-cu 同時報錯兩者互斥只能擇一，兩條 Azure 路徑不能並存
輸出中文亂碼輸入編碼偵測不準加 -c UTF-8 強制編碼
外掛沒生效未加 -p / --use-plugins（預設關閉）加旗標；--list-plugins 先確認已安裝
圖片/音訊輸出少一段內容缺 exiftool 或 LLM client設定 EXIFTOOL_PATH；圖片描述需 --llm-client/--llm-model

④ 進階挑戰題

  1. 寫一支 shell script：用 find 掃出所有 PDF，依檔案大小分流——大檔用 -d 走 Document Intelligence、小檔走內建。
  2. 測試 echo -n "hello" | markitdown -x .txt -c utf-16 與不加 -c 的差異，解釋 charset 提示如何改變轉換結果。
  3. 比較 markitdown file.pdf -o out.md 與 markitdown file.pdf > out.md 的行為差異（stdout 緩衝、錯誤輸出位置）。

⑤ 專案級端到端 Worked Example：無伺服器批次轉換作業

場景：把 CLI 當成無狀態執行單元，組一個「每晚自動批次轉換」的排程作業（scheduled-batch）。 重點是把 CLI 的退出碼、stdin、-o 與系統排程器組合起來——端到端整合 Docker、案例 golden 驗證與安全。

#!/usr/bin/env bash
# scripts/nightly-batch.sh —— cron 排程入口
set -euo pipefail
IN_DIR=/srv/uploads; OUT_DIR=/srv/kb; LOG=/var/log/md-batch.log
mkdir -p "$OUT_DIR" "$(dirname "$LOG")"

# 1. 依檔案大小分流：<5MB 併發跑內建，>=5MB 單獨排隊（避免記憶體尖峰）
find "$IN_DIR" -name '*.pdf' -size -5M -print0 |
  xargs -0 -P4 -I{} sh -c 'markitdown "{}" -o "$OUT_DIR/$(basename "{}" .pdf).md"' >>"$LOG" 2>&1

# 2. 空輸出 = 假成功 → 當失敗處理
find "$OUT_DIR" -name '*.md' -empty -print0 | xargs -0 -r -I{} sh -c 'echo "EMPTY {}" >>"$LOG"; exit 1'

# 3. 健康報告：列出最近 50 行 + 摘要
tail -n 50 "$LOG"
# cron: 0 3 * * * /opt/md-batch/scripts/nightly-batch.sh
# 預期輸出（日誌節錄）
[03:00:01] batch start · 1,204 files
[03:12:44] batch done · 1,204/1,204 · 0 FAIL · 3 EMPTY(rescanned as scanned-PDF)
[03:12:45] exit code 0

為什麼這是「整專案規模」：第 1 輪是「一次批次 + CI 守門」； 這裡把排程、分流、並行、假成功偵測、日誌、退出碼組合成可長期維運的作業—— cron 到點跑、失敗自動重試、空輸出當錯誤，整條鏈不需要任何常駐服務。

⑥ 效能／品質／安全深度：CLI 作業的三面考量

  • 效能：xargs -P 平行度要配合記憶體——PDF 轉換每個 process 吃數百 MB， 並行數過高會 OOM。實務上 -P4 起測，再用 time 量測調校； 大檔與小檔分流是避免「一個巨檔拖住整隊」的關鍵。
  • 品質：CLI 的退出碼是唯一的品質契約——但假成功不反映在退出碼（掃描 PDF 照樣 exit 0）。 所以「空輸出檢查」是 CLI 品質閘的必修課；搭配 --list-plugins 確認外掛真的載入。
  • 安全：檔名直接進 shell 有注入風險（$(...) 或分號）——用 find -print0 + xargs -0、 並在腳本內做路徑白名單；markitdown 吃 URL 時也一樣會抓取，別把不可信 URL 直接餵給 CLI。
