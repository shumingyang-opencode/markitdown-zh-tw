Docker

不污染本機 Python 環境，一行指令把檔案丟進容器轉換

建映像與使用

# 從 repo 根目錄（含 Dockerfile）建映像
docker build -t markitdown:latest .

# stdin 管道轉換
docker run --rm -i markitdown:latest < ~/your-file.pdf > output.md

docker 版本非常適合：不想在本機裝 Python 依賴、或需要乾淨隔離（配合外掛/多版本）的場景。

markitdown-mcp 的 Docker 用法

# 建映像
docker build -t markitdown-mcp:latest .

# 啟動（遠端 URI 即可，本機檔案需掛載）
docker run -it --rm markitdown-mcp:latest

# 掛載本機目錄：容器內以 /workdir 存取
docker run -it --rm -v /home/user/data:/workdir markitdown-mcp:latest

搭配 Claude Desktop

{
  "mcpServers": {
    "markitdown": {
      "command": "docker",
      "args": ["run", "--rm", "-i", "-v", "/home/user/data:/workdir", "markitdown-mcp:latest"]
    }
  }
}
安全提示：容器預設無法存取本機檔案；掛載目錄等於把該路徑開放給容器內程序。 只掛載需要的目錄，並注意 markitdown-mcp 無認證機制。

概念解說

Docker 模式的核心價值是環境隔離：不污染本機 Python 環境， 所有依賴（pdfminer、mammoth、openpyxl…）都封裝在容器映像中。 適用場景：(1) 不想在本機裝依賴、(2) 需要乾淨隔離（配合外掛/多版本）、 (3) CI/CD 管線中使用。

容器預設無法存取本機檔案——需要掛載目錄（-v）才能讀寫。

實際操作 Worked Example

步驟 1：建映像

# 從 repo 根目錄（含 Dockerfile）建映像
docker build -t markitdown:latest .

步驟 2：轉換本機檔案（stdin 管道）

# 用 stdin 管道把 PDF 送進容器
docker run --rm -i markitdown:latest < report.pdf > report.md

# 或掛載目錄
docker run --rm -v $(pwd):/workdir markitdown:latest \
  markitdown /workdir/report.pdf -o /workdir/report.md

步驟 3：markitdown-mcp Docker

# 啟動 MCP server
docker run -it --rm -v $(pwd):/workdir markitdown-mcp:latest

常見錯誤與除錯

容器內找不到檔案
確認 -v 掛載路徑正確。容器內以掛載點為根目錄存取，不是本機路徑。
映像建置失敗
確認 Dockerfile 在 repo 根目錄。常見問題：Docker daemon 未啟動、磁碟空間不足。

練習與驗收

  1. 建好映像後，用 docker run --rm markitdown:latest markitdown --help 確認 CLI 可用。
  2. 掛載一個目錄，轉換其中的 PDF，確認輸出寫回掛載點。
  3. 用 docker images | grep markitdown 確認映像大小。

① 進階真實情境：容器化批次管線 + 掛載資料卷 + CI 排程

場景：你有一個「每晚自動把上傳目錄的檔案轉成 Markdown」的批次任務。 要跑在 CI（如 GitHub Actions）或 cron 上，並保證每次執行環境完全一致。

# 1. 批次轉換腳本（掛載資料卷）
docker run --rm \
  -v "$(pwd)/uploads:/in:ro" \
  -v "$(pwd)/out:/out:rw" \
  markitdown:latest \
  sh -c 'for f in /in/*.pdf; do markitdown "$f" -o "/out/$(basename "${f%.pdf}").md"; done'
# 2. 整合進 CI：環境一致 + 可重現
# .github/workflows/convert-nightly.yml 節錄
- name: Convert uploads
  run: |
    docker build -t markitdown:latest .
    docker run --rm -v "$PWD/uploads:/in:ro" -v "$PWD/out:/out" \
      markitdown:latest sh -c 'for f in /in/*; do markitdown "$f" -o "/out/$(basename "$f").md"; done'
- name: Verify outputs
  run: test -s out/*.md || exit 1

為什麼選這條路徑：容器把依賴版本、系統工具（exiftool）、Python 環境全部封裝—— CI 與本機的結果才可能一致。用 :ro 唯讀掛載輸入目錄，避免批次任務意外改動原始檔； 輸出目錄用 :rw 寫回主機。這是「隔離執行、資料外流」的標準容器模式。

② 深入原理擴充：映像內容與「容器 vs 本機」的差異來源

理解 Dockerfile 裝了什麼，才能預測容器行為：

  • 映像建置會 pip install markitdown[all]（含 pdfminer、mammoth、openpyxl 等）， 所以容器內所有格式都可用——本機沒裝 extras 的差異在容器內不存在。
  • exiftool 是否裝入映像，決定圖片/音訊 EXIF 輸出是否為空。
  • 容器預設使用者是 root；-v 掛載後，容器內寫出的檔案權限歸屬可能與你預期不同。
大家以為轉換沒問題但其實丟資訊
stdin 管道 + 忘了 -i 是容器化最常踩的坑：docker run markitdown:latest < file.pdf 沒加 -i，stdin 是空的——命令「執行成功」但輸出空字串，你以為轉好了其實什麼都沒讀到。 同理，容器預設不掛載本機目錄，file.pdf 路徑在容器內不存在， 轉換失敗的原因常常是路徑，不是轉換器。

③ 診斷式疑難排解表

症狀可能原因解決方案
容器內找不到輸入檔未掛載目錄或路徑寫錯加 -v $(pwd):/workdir，容器內用 /workdir/... 路徑
stdin 管道轉出空字串忘了 -i（interactive）docker run --rm -i markitdown:latest < file.pdf
映像無法建置Dockerfile 不在根目錄 / daemon 未啟動 / 磁碟滿確認 Dockerfile 位置、docker info、清理空間
容器寫出的檔案權限怪異容器以 root 執行加 --user $(id -u):$(id -g) 或調整掛載目錄權限
圖片/音訊輸出缺 EXIF 段映像內沒裝 exiftool在 Dockerfile 加 RUN apt-get install -y exiftool 或設定 EXIFTOOL_PATH

④ 進階挑戰題

  1. 寫一個 docker-compose.yml：掛載輸入輸出目錄、限制 read_only、設定 non-root user，重現批次轉換管線。
  2. 設計一個「多版本測試」：同一台機器跑 markitdown:0.1.6 與 markitdown:latest 兩個容器，比較輸出差異。
  3. 實作「映像瘦身」：用 multi-stage build 只保留執行所需依賴，量測減少的映像大小。

⑤ 專案級端到端 Worked Example：容器化文件轉換農場 + 資源限制 + 日誌聚合

場景：你的公司有 5 台伺服器，每台跑一個 Docker 容器做批次轉換。 容器要限制記憶體（避免 pdfminer 吃光 RAM）、限制 CPU（避免影響其他服務）、 並把日誌聚合到中央——出問題時能追溯到單一檔案。

# 1. docker-compose.yml —— 生產級轉換農場
version: "3.8"
services:
  converter:
    image: markitdown:latest
    deploy:
      resources:
        limits:
          memory: 512M       # pdfminer 每個 process 約 200-400MB
          cpus: "0.5"        # 限半核，避免拖慢主機
    volumes:
      - ./uploads:/in:ro     # 唯讀：不允許改動原始檔
      - ./output:/out:rw     # 可寫：轉換結果
      - ./logs:/var/log/md:rw
    read_only: true          # 只讀根檔案系統
    tmpfs:
      - /tmp:size=100M       # 暫存空間（ZIP 解壓等）
    user: "1000:1000"        # 非 root
    command: >
      sh -c 'for f in /in/*.pdf; do
        markitdown "$f" -o "/out/$(basename "${f%.pdf}").md" 2>>/var/log/md/convert.log;
      done'
# 2. 批次執行 + 日誌聚合（5 台機器的統一入口）
#!/usr/bin/env bash
set -euo pipefail
SERVERS=("srv1" "srv2" "srv3" "srv4" "srv5")
for srv in "${SERVERS[@]}"; do
  ssh "$srv" "cd /opt/md-farm && docker compose run --rm converter" &
done
wait
# 聚合所有機器的日誌
for srv in "${SERVERS[@]}"; do
  scp "$srv:/opt/md-farm/logs/convert.log" "logs/${srv}.log"
done
cat logs/*.log | sort | uniq -c | sort -rn > logs/summary.log
# 3. 預期輸出（日誌聚合）
  1,847 SUCCESS
    153 FAIL (empty output)
      3 FAIL (ModuleNotFoundError)
# 退出碼：0=全成功，1=有失敗，2=容器啟動失敗

為什麼這是「整專案規模」：第 1 輪是「單一容器批次」； 這裡是多機器、資源隔離、非 root、唯讀根、日誌聚合的生產級部署—— 容器不只是「跑得起來」，還要「不拖垮主機、不洩漏資料、出問題能追溯」。

⑥ 效能／品質／安全深度：容器化的三面考量

  • 效能：Docker 映像的首次啟動成本（pull + 初始化）約 3-10 秒， 批次處理時用 docker compose run 而非 docker run 可共用網路/卷設定。 multi-stage build 可把映像從 ~1GB 瘦身到 ~300MB（只留執行時依賴）。 併發時注意：容器間共享主機 I/O，過多並行會互相干擾。
  • 品質：容器的環境一致性是品質的基礎—— 本機跑 0.1.7、容器跑 0.1.6 的「版本漂移」會導致輸出差異。 用 markitdown -v 釘版本、在 CI 中用相同映像做回歸測試， 確保「容器 = 本機 = CI」三環境一致。
  • 安全：容器預設以 root 執行——加上 --user 降到非 root。 read_only: true 阻止寫入根檔案系統；tmpfs 提供有限暫存空間。 掛載目錄用 :ro 唯讀——批次任務不該修改原始檔。 不要在映像中硬編碼 API Key，用環境變數或 secret manager。
