安全模型

MarkItDown 的 I/O 權限等同目前程序——請像對待 open() / requests.get() 一樣謹慎
核心風險：MarkItDown 以目前程序的權限執行 I/O。 它會存取「程序本身能存取」的資源——這和 open()、requests.get() 一樣。 在不信任的環境中，輸入必須先驗證與限制。

三條安全守則

1. Sanitize inputs（消毒輸入）

不要把不受信任的輸入直接丟給 MarkItDown。在代管 / 伺服器應用中，任何可能受使用者控制的輸入， 都必須先驗證與限制，例如：

  • 限制檔案路徑範圍（擋掉絕對路徑、.. 穿越）
  • 限制 URI scheme 與網路目的地
  • 封鎖私有、loopback、link-local、metadata-service 位址（如 169.254.169.254）

2. 呼叫最窄的 convert_* 函數

convert() 故意很寬鬆：可吃本機檔、遠端 URI、bytes 流。請依用途收窄：

你的需求該用
只讀本機檔案convert_local()
自己控制 URI 抓取（proxy/驗證/快取）自己 requests.get() → convert_response()
最大控制權自己 open stream → convert_stream()

3. 信任你的 converter

第三方外掛的 convert() 會以你的權限執行任意程式碼——只安裝信任來源的外掛。 accepts() 也一樣是外部程式碼。

markitdown-mcp 的額外風險面

  • 伺服器無認證，以執行者權限運作。
  • HTTP/SSE 預設綁 localhost，但同機其他程序仍可呼叫。
  • convert_to_markdown 能讀伺服器使用者可讀的任何檔案 + 任何網路資料。
  • 需要更高安全：放進 VM/容器沙箱、限制使用者權限；不要綁到非 localhost 介面。

官方原文

English original — Security Considerations
MarkItDown performs I/O with the privileges of the current process. Like open() or requests.get(), it will access resources that the process itself can access.
Do not pass untrusted input directly to MarkItDown. If any part of the input may be controlled by an untrusted user or system, such as in hosted or server-side applications, it must be validated and restricted before calling MarkItDown. Depending on your environment, this may include restricting file paths, limiting URI schemes and network destinations, and blocking access to private, loopback, link-local, or metadata-service addresses.
Prefer the narrowest conversion API that fits your use case. MarkItDown's convert() method is intentionally permissive and can handle local files, remote URIs, and byte streams. If your application only needs to read local files, call convert_local() instead. If you need more control over URI fetching, call requests.get() yourself and pass the response object to convert_response(). For maximum control, open a stream to the input you want converted and call convert_stream().

概念解說

MarkItDown 的安全模型核心：I/O 權限等同目前程序。 它會存取「程序本身能存取」的資源——這和 open()、requests.get() 一樣。 三條守則：(1) 消毒輸入、(2) 只用最窄的 convert_* 函數、(3) 信任你的 converter。

最容易忽略的風險是路徑穿越：使用者傳入 ../../etc/passwd 這類路徑時， MarkItDown 會照樣讀——因為它只是執行 open()。伺服器應用必須先驗證路徑。

實際操作 Worked Example

步驟 1：示範路徑穿越風險

from markitdown import MarkItDown
md = MarkItDown()
# 危險：直接把使用者輸入丟給 convert()
result = md.convert(user_input)  # user_input = "../../etc/passwd"

步驟 2：正確做法——限制路徑範圍

import os
from markitdown import MarkItDown

SAFE_DIR = "/data/uploads"
user_input = "../../etc/passwd"

# 先驗證：解析路徑、確認在安全目錄內
resolved = os.path.realpath(os.path.join(SAFE_DIR, user_input))
if not resolved.startswith(os.path.realpath(SAFE_DIR)):
    raise ValueError("路徑穿越！")

md = MarkItDown()
result = md.convert_local(resolved)  # 用最窄的 convert_local()

步驟 3：限制 URI scheme

from urllib.parse import urlparse

def safe_convert_uri(md, uri):
    parsed = urlparse(uri)
    if parsed.scheme not in ("http", "https", "file"):
        raise ValueError(f"不支援的 scheme: {parsed.scheme}")
    if parsed.hostname in ("169.254.169.254", "localhost", "127.0.0.1"):
        raise ValueError("封鎖私有位址")
    return md.convert_uri(uri)

常見錯誤與除錯

SSRF 風險
convert_uri() 能讀任何 URL，包括內網位址。伺服器應用必須封鎖 loopback、link-local、metadata-service（169.254.169.254）。
外掛 = 任意程式碼執行
第三方外掛的 convert() 會以你的權限執行。只安裝信任來源的外掛。

練習與驗收

  1. 寫一個函數：接收使用者路徑，驗證在安全目錄內後才呼叫 convert_local()。
  2. 測試 convert_uri() 對 http://169.254.169.254/ 的行為。
  3. 比較 convert() 與 convert_local() 的權限範圍差異。

① 進階真實情境：打造安全的檔案轉換 API（消毒 + 白名單 + 沙箱）

場景：你要把 MarkItDown 包成一個對外服務，使用者可上傳檔案、要求轉換。 攻擊面很大——路徑穿越、SSRF、外掛任意碼執行。以下是「安全地包裝」的完整工作流。

import os, io
from pathlib import Path
from urllib.parse import urlparse
from markitdown import MarkItDown

ALLOWED_DIR = Path("/data/uploads").resolve()

def safe_local(path_str: str) -> Path:
    # 1. 消毒輸入：解析路徑並確認在允許目錄內（擋 . . / 穿越）
    p = (ALLOWED_DIR / path_str).resolve()
    if not p.is_relative_to(ALLOWED_DIR):
        raise ValueError("path traversal blocked")
    return p

def safe_uri(uri: str):
    # 2. 限制 scheme + 封鎖私網位址（防 SSRF）
    parsed = urlparse(uri)
    if parsed.scheme not in ("http", "https"):
        raise ValueError("scheme not allowed")
    if parsed.hostname in ("localhost", "127.0.0.1") or \
       parsed.hostname == "169.254.169.254" or \
       parsed.hostname.startswith("10."):
        raise ValueError("private/metadata address blocked")
    return uri

# 3. 只用最窄 API + 禁止外掛（外掛 = 任意程式碼）
md = MarkItDown(enable_plugins=False)

def handle_upload(filename: str):
    p = safe_local(filename)
    return md.convert_local(str(p)).markdown

def handle_url(url: str):
    # 4. 自己抓取、設 timeout、再交給 convert_response
    import requests
    resp = requests.get(safe_uri(url), timeout=30)
    resp.raise_for_status()
    return md.convert_response(resp).markdown

為什麼選這條路徑：安全不是「一個函數」，是一層層消毒與收窄—— 先驗證路徑/scheme，再關掉外掛，最後只用最窄 API。每一層都擋住一類攻擊： 路徑穿越（path traversal）、SSRF（metadata service、內網）、任意程式碼執行（plugin）。

② 深入原理擴充：MarkItDown 的四個攻擊面

把 MarkItDown 當成黑盒只會「出事才發現」。先畫出攻擊面：

  • 檔案路徑：convert_local() 只是 open() 的包裝——../../etc/passwd 會照讀。
  • URI：convert_uri() 的 file: 會解成本機路徑（netloc 非 localhost 才擋），http(s): 會抓內網或 metadata service。
  • data URI：base64 解碼成 bytes 再轉換——巨大 payload 可造成記憶體耗用。
  • 外掛：accepts() / convert() 都是外部程式碼，會以你的權限執行。
大家以為轉換沒問題但其實丟資訊（或洩密）
「我只是轉個網頁」的 SSRF：使用者傳 http://169.254.169.254/latest/meta-data/ （雲端 metadata 服務），convert_uri() 會真的去抓——那不是「轉換失敗」， 是把你的內網/雲端憑證資訊洩露進輸出。攻擊面最大的誤區是：以為 MarkItDown 只讀檔案， 其實 convert() 可以觸發本機檔 + 網路 + base64 解碼三種 I/O。

④ 進階挑戰題

  1. 寫一組測試：對 safe_local() 餵 ../../etc/passwd、絕對路徑、符號連結，驗證全部被擋。
  2. 實作一個「data URI 大小限制」的包裝器：超過 1MB 直接拒絕，不進入 MarkItDown。
  3. 設計「深度防禦」架構圖：Web 層（消毒）→ 轉換層（最窄 API、無外掛）→ 沙箱層（容器/VM），標出每一層擋住哪種攻擊。

⑤ 專案級端到端 Worked Example：零信任文件轉換架構

場景：你要把 MarkItDown 部署在零信任環境——使用者可上傳任意檔案、 任意 URL，你不信任任何輸入。架構需要四層防禦： Web 驗證層 → 路由消毒層 → 轉換執行層 → 輸出審計層。 每一層各自獨立，壞一層不拖垮其他層。

# 1. 四層防禦架構（zero_trust_doc_svc.py）
import os, io, hashlib, time
from pathlib import Path
from urllib.parse import urlparse
from markitdown import MarkItDown
from markitdown._exceptions import FileConversionException

# ── 第一層：Web 驗證層（擋格式、大小、速率）──
MAX_SIZE = 50 * 1024 * 1024  # 50MB
ALLOWED_EXTS = {".pdf", ".docx", ".xlsx", ".pptx", ".csv", ".html"}

def validate_input(filename: str, size: int) -> str:
    ext = Path(filename).suffix.lower()
    if ext not in ALLOWED_EXTS:
        raise ValueError(f"格式不允許: {ext}")
    if size > MAX_SIZE:
        raise ValueError(f"檔案太大: {size} bytes > {MAX_SIZE}")
    return ext

# ── 第二層：路由消毒層（路徑白名單 + URI 篩選）──
SAFE_DIR = Path("/data/uploads").resolve()

def sanitize_path(user_path: str) -> Path:
    resolved = (SAFE_DIR / user_path).resolve()
    if not resolved.is_relative_to(SAFE_DIR):
        raise ValueError("路徑穿越")
    return resolved

def sanitize_uri(uri: str) -> str:
    parsed = urlparse(uri)
    if parsed.scheme not in ("http", "https"):
        raise ValueError(f"scheme 不允許: {parsed.scheme}")
    blocked = {"169.254.169.254", "localhost", "127.0.0.1",
               "0.0.0.0", "metadata.google.internal"}
    if parsed.hostname in blocked:
        raise ValueError("封鎖私有/元資料位址")
    return uri

# ── 第三層：轉換執行層（最窄 API + 無外掛 + 超時）──
md = MarkItDown(enable_plugins=False)  # 關外掛 = 關任意碼執行

def safe_convert(path: Path) -> str:
    result = md.convert_local(str(path))
    return result.markdown

# ── 第四層：輸出審計層（記錄摘要、不記錄內容）──
def audit_log(path: str, status: str, chars: int):
    entry = f"{time.strftime('%Y-%m-%d %H:%M')} | {status} | {chars} chars | {hashlib.sha256(path.encode()).hexdigest()[:12]}"
    with open("/var/log/md-audit.log", "a") as f:
        f.write(entry + "\n")
# 2. 整合四層 + 預期輸出
try:
    ext = validate_input("report.pdf", os.path.getsize("report.pdf"))
    safe_path = sanitize_path("report.pdf")
    text = safe_convert(safe_path)
    audit_log("report.pdf", "OK", len(text))
except (ValueError, FileConversionException) as e:
    audit_log("report.pdf", f"BLOCKED: {e}", 0)

# 預期輸出（日誌）
# 2026-08-17 10:00 | OK | 12840 chars | a3f2c...
# 2026-08-17 10:01 | BLOCKED: 路徑穿越 | 0 chars | b7e1d...

為什麼這是「整專案規模」：第 1 輪是「單一消毒函數」； 這裡是四層獨立防禦 + 審計日誌 + 格式白名單 + 大小限制—— 每一層只做一件事，壞一層不影響其他層。審計日誌記錄雜湊而非內容， 兼顧追蹤與隱私。這是在「不信任任何輸入」的前提下，把 MarkItDown 安全包裝的完整架構。

⑥ 效能／品質／安全深度：安全措施的三面代價

  • 效能：每一層防禦都有成本——路徑 resolve() 做一次檔案系統呼叫、 URI 解析做字串處理、格式白名單做集合查找。實測約增加 1-5ms/請求（可忽略）。 真正的瓶頸在轉換本身（pdfminer 秒級），安全層的 overhead 不是瓶頸。
  • 品質：安全措施可能降低可用性——格式白名單太嚴格會擋掉合法但罕見的格式 （如 .doc 舊版 Word）、大小限制會擋掉大型報告。 品質與安全的平衡：白名單太寬 = 風險高、太窄 = 用不了。 建議：初始白名單只放最常見格式，有需求再逐步放寬，每次放寬都做風險評估。
  • 安全：「零信任」的代價是複雜度——四層防禦每一層都要測試、維護、更新。 路徑穿越的 resolve() 在不同 OS 行為不同（符號連結、大小寫）； URI 黑名單可能遺漏新的私有位址範圍（如 IPv6 link-local）。 定期做滲透測試（penetration test）是驗證防禦有效的唯一方法——寫再多代碼也不保證安全。
