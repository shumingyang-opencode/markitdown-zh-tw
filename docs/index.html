① 進階真實情境：設計你的第一個「端到端」轉換專案

場景：你不是為了學 API，而是要解決一個真實問題——「把散落的會議文件變成可搜尋的知識庫」。 以這個目標為嚮導，把本頁所有主題串成一個專案，每個主題都是一個可驗收的里程碑。

# 專案：會議知識庫 (meeting-kb)
# 目標：一份 CI 腳本，把 uploads/ 的 PDF/DOCX/XLSX 轉成 Markdown，品質驗證後 commit 進知識庫

# 里程碑 1（運作原理 + 架構）: 用 CLI 批次轉換，觀察輸出結構
markitdown uploads/agenda.docx -o kb/agenda.md
markitdown uploads/minutes.pdf -o kb/minutes.md

# 里程碑 2（Python API + 外掛）: 寫 Python 批次器，加上品質閘與失敗分類
python scripts/ingest.py --dir uploads --out kb

# 里程碑 3（安全 + Docker）: 包成容器跑 cron，加入路徑消毒，確認不處理不可信輸入
docker run --rm -v "$PWD/uploads:/in" -v "$PWD/kb:/out" meeting-kb:latest

為什麼選這條路徑：教學頁的知識是分塊的，專案是把它們縫合起來的針線。 每一步都對應一頁的主題，而「品質閘」「失敗分類」「路徑消毒」這些跨頁概念， 只有在真實專案裡才會真正內化。做完這個專案，你就知道自己哪些頁其實沒讀懂。

② 深入原理擴充：學習地圖的「依賴順序」設計

本站的學習路線不是隨意排列的，背後是概念依賴圖：

  • 運作原理 → 架構：先懂「一條管線」的調度，再看「管線由哪些套件組成」。
  • 轉換器 → CLI/API：先懂「22 個黑箱各自做什麼」，再學怎麼呼叫它們。
  • 外掛 → MCP → 雲端：先懂「可插拔」，再看「如何包成服務、如何上雲」。
  • 安全最後：安全不是功能，是約束其他所有功能的邊界——最後讀才知道該防什麼。
大家以為轉換沒問題但其實丟資訊
「讀完 ≠ 會用」的認知落差：很多人看完所有頁面，就以為「只要一行 convert() 就能解決所有格式」。 真相是：掃描 PDF 需要雲端、圖片描述需要 LLM、音訊轉錄需要外部 API、合併格會被攤平—— 沒有「免費且完美」的轉換。教學站的功能是告訴你每個選擇的取捨，而不是承諾魔法。 若你跳過「限制與常見錯誤」小節，就會在真實資料上踩坑。

⑤ 專案級端到端 Worked Example：五階段企業文件知識庫

場景：把全站知識縫合成一個可營運的系統——「企業文件知識庫」（enterprise-doc-kb）。 規模假設：每天 +500 份文件、3 萬份歷史文件、5 個部門共用。與第 1 輪「單一管線」不同， 這裡是整專案規模：每一階段對應本站不同 docs 頁，逐段可驗收。

# 專案：enterprise-doc-kb（企業文件知識庫）

# ── 階段 1 · 環境與基線（install + cli）──
pip install 'markitdown[all]'
markitdown -v                                  # 釘版本：v0.1.7
markitdown sample.docx -o sample.md            # 手動基線：確認輸出結構

# ── 階段 2 · 批次管線（python-api + how-it-works）──
python scripts/ingest.py --dir uploads --out kb/
# 逐檔 convert_local() + 格式特定品質閘 + 例外分類收集

# ── 階段 3 · 品質與補強（converters + cloud）──
# 掃描 PDF 被品質閘攔下 → 標記 needs-ocr → CU 補償升級
# XLSX 合併格 NaN 語意 → 記錄已知失真，不當作錯誤

# ── 階段 4 · 服務化（mcp + docker + security）──
docker compose up -d                           # 轉換器 + MCP + 排程器
# agent 透過 markitdown-mcp 查詢；輸入層消毒路徑/URI

# ── 階段 5 · 索引與維運（worked + 監控）──
python scripts/index.py --dir kb/ --index es   # 寫入檢索索引
python scripts/quality_report.py --since 7d    # 每週品質報表
# 預期輸出（階段驗收）

[2] 管線: 30000/30000 完成 · OK 96% · LOW-Q 3% · FAIL 1%
[3] 品質: 掃描 PDF 升級率 <5% · 平均字數 >500

[5] 索引: 30000 篇已索引 · 檢索延遲 P95 <200ms
為什麼這是「整專案規模」：第 1 輪的案例是「一個功能」， 這裡是「一個產品」——環境、批次、品質、服務、維運五條線並行， 每一條線都是對應 docs 頁知識的完整應用；最後的品質報表把整個專案變成可量測的系統。

⑥ 效能／品質／安全深度

  • 效能：批次管線三大瓶頸——重複建 MarkItDown() 實例（應建一次重用）、 IO 密集（用 Path.rglob + worker 併發）、LLM/雲端呼叫（只對品質閘攔下的檔案觸發）。 以 3 萬份歷史檔估算：純本機約 30–60 分鐘，加入 CU 升級後視升級率決定額外成本。
  • 品質：品質不是「有輸出」，是「結構完整」——DOCX 至少一個 #、XLSX 至少一個 | 表格、 PDF 用「頁數 vs 字數」對照抓掃描件假成功。把驗證寫成可重跑的自動化，不靠肉眼。
  • 安全：輸入即攻擊面——上傳路徑做 realpath 白名單、URL 擋 metadata service （169.254.169.254）、enable_plugins=False（第三方外掛=任意碼執行）。詳見安全模型。

⑤ 專案級端到端 Worked Example：全端企業文件處理系統

場景：你不是只學 API，而是要交付一個完整的產品——「企業文件處理系統」 （enterprise-doc-processor），涵蓋前端上傳、後端轉換、品質驗證、索引寫入、監控告警五個子系統。 每個子系統對應本站至少一個 docs 頁的知識，串起來就是一整套可交付的系統。

⑥ 效能／品質／安全深度：跨頁主題的三面交織

  • 效能：跨頁的效能瓶頸在轉換本身（pdfminer 秒級、CU 分鐘級）， 而不是安全層（毫秒級）或監控層（非同步）。 優化策略：(1) MarkItDown() 建一次重用（避免重複初始化）、 (2) 本機先試 + CU 只補償（減少付費呼叫）、 (3) 併發用 process pool 而非 thread pool（_convert() 非執行緒安全）。
  • 品質：品質不是「有輸出」，是「結構完整 + 語意保留」—— 本站反覆強調的「假成功」（掃描 PDF 空字串、XLSX 合併格 NaN）， 只有在「格式特定品質閘」下才被發現。通用字數閘擋不住結構問題。 品質閘必須每種格式各寫一個——這是「沒有免費且完美轉換」的最直接體現。
  • 安全：安全不是一個功能，是約束其他所有功能的邊界—— 路徑消毒約束了上傳、格式白名單約束了轉換、非 root 約束了容器、 enable_plugins=False 約束了外掛、localhost 綁定約束了 MCP。 每個約束都「限制了某些便利」，但每個約束都「擋住了某種攻擊」。 安全的代價是複雜度——需要持續測試、更新、滲透驗證。
